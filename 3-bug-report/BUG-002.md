# BUG-002: Latencia excesiva en endpoints de escritura (10-18 segundos)

**Severidad:** Media-Alta
**Prioridad:** Alta
**Componente:** API Gateway — `POST /v1/login`, `POST /v1/mdm_psc/punches/replace_punches`
**Ambiente:** QA (https://demo.timekeeper.goodrabbit.tech)
**Reportado por:** Paula Gallardo Carrasco
**Fecha:** 24-25 de septiembre de 2026

---

## Resumen

Los endpoints de escritura (`POST`) probados presentan tiempos de respuesta muy por encima de lo aceptable para una API REST (referencia habitual: menos de 1-2 segundos). Se midió consistentemente entre 10 y 18 segundos en dos endpoints distintos, en múltiples ejecuciones, tanto en solicitudes exitosas como fallidas, lo que descarta un evento aislado y apunta a un problema estructural del ambiente.

## Pasos para reproducir

1. Autenticarse en `POST /v1/login` con credenciales válidas. Medir el tiempo de respuesta.
2. Intentar `POST /v1/login` con una contraseña incorrecta. Medir el tiempo de respuesta.
3. Ejecutar `POST /v1/mdm_psc/punches/replace_punches` con un body válido. Medir el tiempo de respuesta.
4. Repetir el paso 3 una segunda vez, para descartar que sea un evento único (cold start).

## Resultado esperado

Tiempos de respuesta por debajo de 1-2 segundos para operaciones de escritura simples, sin llamadas a servicios externos evidentes en el contrato del endpoint. La latencia no debería depender de si la operación tiene éxito o falla.

## Resultado actual

| Endpoint | Caso | Tiempo de respuesta | Código |
|---|---|---|---|
| `POST /v1/login` | Credenciales correctas | 12.10 s | 200 |
| `POST /v1/login` | Credenciales incorrectas (NEG-02) | **18.61 s** | 400 |
| `POST /v1/mdm_psc/punches/replace_punches` | Ejecución 1 | 10.52 s | 200 |

Para contraste, otros endpoints del mismo ambiente responden en tiempos normales (`GET /v1/employee/employee`: 303 ms; `GET /v1/timekeeper/punch_match`: 479 ms; `POST /v1/schedule/shift/assign`: dentro de 1.5 s; `POST /v1/employee/employee/create` exitoso: 679 ms; `[NEG-03]` Assign sin token: 221 ms; `[NEG-04]` Assign a empleado inexistente: 521 ms), lo que confirma que el problema no es generalizado a toda la API, sino específico de `login` y `replace_punches`.

## Análisis

- La latencia se repite de forma consistente entre ejecuciones de un mismo endpoint, lo que descarta un evento puntual (cold start, timeout de red).
- **Es igual de lenta cuando el login falla** (18.61 s con clave incorrecta) que cuando tiene éxito (12.10 s), lo que sugiere que el cuello de botella ocurre **antes** de completar la validación de credenciales — posiblemente en un paso previo compartido (por ejemplo, una consulta o negociación con un servicio de autenticación externo) y no en la lógica de negocio del login en sí.
- `replace_punches` también valida el token de autorización antes de procesar, por lo que podría compartir el mismo cuello de botella subyacente que el login, aunque no se confirmó una causa común exacta sin acceso a los logs del backend.

## Impacto

Una latencia de 10 a 18 segundos por operación es inaceptable para el uso normal del dashboard: un usuario que inicia sesión o registra una marcación esperaría una respuesta casi inmediata, y una espera de casi 20 segundos ante una contraseña incorrecta agrava la mala experiencia justo en el momento de mayor fricción para el usuario. En un escenario de uso real con múltiples usuarios concurrentes, este tiempo probablemente se degrade aún más — pregunta que se explora en el bonus de pruebas de carga (k6) de este challenge.

## Hallazgo secundario (mismo endpoint, distinto tipo de problema)

Durante la prueba de `replace_punches` se observó además que **`disable_ids` con un valor inexistente no genera error ni advertencia**: al enviar `"disable_ids": [78]` (un ID que no existe en este ambiente, donde los `punch_match_id` reales van de 1 a 8), la respuesta fue `200 OK` con `"disable_punches": []` (vacío), sin indicar que el ID no se encontró. El ejemplo de respuesta incluido en la colección Postman entregada muestra que, cuando el ID sí existe, este campo devuelve el registro deshabilitado con su detalle completo.

**Riesgo:** quien use este endpoint puede asumir que una marca fue deshabilitada exitosamente cuando en realidad no ocurrió nada, sin ninguna señal de error. Se sugiere evaluar si amerita un reporte separado o una mejora de la respuesta (por ejemplo, listar los IDs no encontrados en un campo `not_found_ids`).
