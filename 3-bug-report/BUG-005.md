# BUG-005: Los turnos se muestran con un desfase de horas respecto a lo asignado (manejo inconsistente de zona horaria)

**Severidad:** Alta
**Prioridad:** Alta
**Componente:** API Scheduler (`POST /v1/schedule/shift/assign`) — Dashboard Web (Hoja de Horas)
**Ambiente:** QA (https://demo.timekeeper.goodrabbit.tech)
**Reportado por:** Paula Gallardo Carrasco
**Fecha:** 26 de septiembre de 2026
**Encontrado mediante:** validación cruzada API → Dashboard Web

---

## Resumen

Al asignar un turno de **13:00 a 22:00** (hora `America/Santiago`) mediante `POST /v1/schedule/shift/assign`, el Dashboard Web muestra el turno como **10:00 a 19:00** en la sección "Hoja de Horas", un desfase de 3 horas. El turno que el sistema realmente registra y le muestra al trabajador **no coincide** con el horario que el administrador intentó asignar.

## Pasos para reproducir

1. Autenticarse en `POST /v1/login`.
2. Enviar `POST /v1/schedule/shift/assign` con el siguiente body, para el empleado 1, con el turno definido en hora local de Chile pero los segmentos marcados en UTC:
   ```json
   {
     "shift": {
       "employee_id": 0,
       "date": "2026-09-10",
       "start_ts": "13:00:00",
       "end_ts": "22:00:00",
       "duration": "09:00:00",
       "timezone": "America/Santiago",
       "override": false,
       "schedule_create": true,
       "enable": true,
       "segments": [
         {
           "type": "REGULAR",
           "start_ts": "2026-09-10T13:00:00.000Z",
           "end_ts": "2026-09-10T22:00:00.000Z"
         }
       ]
     },
     "employee_ids": [1],
     "repeat": 2
   }
   ```
3. Confirmar en la respuesta que el turno se creó con `"start_ts": "13:00:00"`, `"end_ts": "22:00:00"` y `"timezone": "America/Santiago"`.
4. Abrir el Dashboard Web → Control de Tiempo → **Hoja de Horas**, filtrar por el empleado 1, y observar el horario mostrado para las fechas del turno creado (10 y 11 de septiembre de 2026).

## Resultado esperado

El Dashboard debería mostrar el turno tal como fue asignado: **13:00 - 22:00**.

## Resultado actual

El Dashboard muestra el turno como **10:00 - 19:00**, un desfase de **3 horas** respecto a lo enviado (ver captura en `evidencia/bug-005/`).

## Análisis

El body del request contiene **dos representaciones distintas y contradictorias** de la misma hora:
- `shift.start_ts: "13:00:00"` — un valor de hora "plano", sin marca de zona horaria explícita, acompañado del campo separado `shift.timezone: "America/Santiago"`.
- `segments[].start_ts: "2026-09-10T13:00:00.000Z"` — el mismo `13:00`, pero con el sufijo `Z`, que en formato ISO 8601 indica explícitamente **UTC**, no hora de Chile.

El sistema parece dar prioridad a los `segments` (marcados como UTC) para el registro real del turno, e ignora o subordina el par `start_ts` / `timezone` del nivel superior del `shift`. Al convertir `13:00 UTC` a hora de Chile (`America/Santiago`, en horario de verano UTC-3 para la fecha probada), el resultado es `10:00`, que es exactamente lo que se ve en el Dashboard.

Es decir: quien arma el request (en este caso, siguiendo el propio ejemplo de la colección Postman entregada con el reto) probablemente asume que escribir `13:00:00.000Z` en los `segments` junto con `timezone: "America/Santiago"` en el nivel superior hará que el sistema interprete `13:00` como hora de Chile. En la práctica, el sistema toma la `Z` literalmente como UTC, ignorando la intención expresada en `shift.timezone`.

## Impacto

Este es un defecto de alta severidad porque es **silencioso**: la API responde `200 OK` con un mensaje de éxito, sin ninguna advertencia de que el horario resultante difiere del que se quiso asignar. Un administrador que arme turnos siguiendo el mismo patrón del ejemplo oficial de la colección (que es exactamente lo que se hizo aquí) terminaría asignando turnos sistemáticamente desfasados en 3-4 horas (según la época del año, por el horario de verano/invierno de Chile), afectando directamente el pago de horas y la planificación real de los trabajadores, sin que nadie lo note a menos que compare manualmente contra el Dashboard, como se hizo en esta validación.

## Evidencia

- Respuesta de `assign` con `start_ts: "13:00:00"` (ver `3-bug-report/BUG-001.md` y capturas previas del flujo).
- Captura del Dashboard, sección "Hoja de Horas", mostrando `10:00 - 19:00` para el mismo turno (ver `../evidencias/bug-005/`).

## Recomendación

Definir y documentar explícitamente cuál de los dos campos es la fuente de verdad para la hora del turno (`shift.start_ts` + `shift.timezone`, o `segments[].start_ts` en UTC), y si son ambos, validar en el backend que sean consistentes entre sí, rechazando la solicitud o advirtiendo si no lo son, en vez de aceptarla silenciosamente con el valor de los `segments`.
