# BUG-001: Validación incompleta en creación de empleados — error 409 engañoso por campo requerido no declarado

**Severidad:** Alta

**Prioridad:** Alta

**Componente:** API Employee — `POST /v1/employee/employee/create`

**Ambiente:** QA — `https://demo.timekeeper.goodrabbit.tech`

**Reportado por:** Paula Gallardo Carrasco

**Fecha:** 24–25 de septiembre de 2026

---

## Resumen

El endpoint `POST /v1/employee/employee/create` requiere el campo `pay_period_end` para completar correctamente la creación de un empleado, pero **no lo declara como obligatorio en su validación de esquema (422)**.
Cuando `pay_period_end` no está presente, la petición no falla con un mensaje de validación claro, sino que responde con:
`409 Conflict — { "detail": "Error creating. Integrity error" }`
Este mensaje resulta engañoso, ya que sugiere un conflicto de integridad o duplicidad de datos, cuando el problema reproducible está relacionado con la ausencia de un campo requerido que no es informado por la validación del endpoint.
La causa se identificó comparando un request fallido realizado vía Postman con un request exitoso capturado desde el Dashboard Web mediante DevTools.

---

## Pasos para reproducir

### Caso que falla — 409 engañoso

1. Autenticarse mediante `POST /v1/login`.

2. Enviar `POST /v1/employee/employee/create` con un body que incluya todos los campos que el endpoint identifica como requeridos mediante su respuesta 422, pero sin `pay_period_end`:

```json
{
  "first_name": "Ejemplo",
  "last_name": "Usuario",
  "email": "ejemplo.qa101@goodrabbit.tech",
  "document_type_id": 2,
  "document_employee": "77777777-7",
  "birth_date": "1990-01-01",
  "pay_rule_id": 2,
  "timezone": "America/Santiago"
}
```

3. Resultado:

`409 Conflict`
```json
{
  "detail": "Error creating. Integrity error"
}
```

### Caso que funciona — `pay_period_end` informado

4. Repetir la solicitud agregando `pay_period_end`:

```json
{
  "first_name": "Ejemplo",
  "last_name": "Usuario",
  "email": "ejemplo.qa103@goodrabbit.tech",
  "document_type_id": 2,
  "document_employee": "55555555-5",
  "birth_date": "1990-01-01",
  "pay_rule_id": 1,
  "timezone": "America/Santiago",
  "pay_period_end": "2026-09-23"
}
```

5. Resultado esperado observado:

`200 OK` — empleado creado correctamente (`employee_id: 10`).

> Durante la investigación también se reprodujo el request exitoso capturado desde el Dashboard Web, que incluía `phone_number`, `address` y `pay_period_end`. Posteriormente, las pruebas permitieron aislar `pay_period_end` como el campo requerido para resolver este comportamiento. `phone_number` y `address` no son considerados la causa del 409.

---

## Resultado esperado

Si `pay_period_end` es efectivamente obligatorio para la creación de empleados, el endpoint debería rechazar su ausencia mediante una respuesta `422` y declararlo explícitamente como campo requerido, de la misma forma que actualmente ocurre con `pay_rule_id`, `birth_date`, `document_employee` y `timezone`.

Alternativamente, si el campo no debería ser obligatorio según la regla de negocio, el endpoint debería permitir la creación sin él.

---

## Resultado actual

Cuando `pay_period_end` no está presente, el endpoint responde:

`409 Conflict — "Error creating. Integrity error"`

El mensaje no identifica la causa real del problema y puede llevar al consumidor de la API a investigar un supuesto conflicto de unicidad o integridad en lugar de indicar que falta un dato requerido.

---

## Cómo se aisló la causa raíz

1. Se probaron distintos valores de `email`, `document_employee`, `pay_rule_id` (1 y 2) y `document_type_id` (1 y 2), utilizando valores únicos cuando correspondía. El `409` persistió, reduciendo la probabilidad de que se tratara de un conflicto de unicidad en alguno de esos campos.

2. Se creó un empleado correctamente desde el **Dashboard Web** y se capturó el request mediante DevTools → Network.

3. El request exitoso del Dashboard incluía `phone_number`, `address` y `pay_period_end`, campos que no estaban presentes en las solicitudes iniciales de Postman.

4. Se realizaron nuevas pruebas para aislar el comportamiento y se confirmó que `pay_period_end` es el campo relevante para completar correctamente la creación. `phone_number` y `address` no son necesarios para reproducir ni resolver el problema.

## Impacto

Cualquier integración, script o cliente de API que construya el body de creación basándose únicamente en los campos declarados como requeridos por la respuesta 422 puede recibir un `409 Conflict` sin una explicación clara.

Esto dificulta significativamente el diagnóstico del problema para consumidores de la API que no tengan acceso al código fuente o al Dashboard Web.

Además, la propia colección Postman entregada con el reto contiene un body de ejemplo incompleto, por lo que un consumidor que utilice dicha colección como referencia puede encontrarse con este comportamiento.

---

## Consecuencia adicional confirmada

Los empleados creados mediante este endpoint quedan con `"active": null` en la respuesta y se muestran como **"Inactivo"** en el Dashboard Web.

En ese estado, no aparecen como opción seleccionable en el módulo de Horario/Scheduler para asignación de turnos.

Durante la investigación se comprobó que el estado pasa a **"Activo"** al utilizar posteriormente la acción **"Asignar contrato"** desde el menú de acciones del trabajador.

Esto representa un flujo adicional que ocurre después de la creación del empleado y que no está documentado ni informado por el contrato del endpoint `POST /v1/employee/employee/create`.

Por lo tanto, un consumidor que utilice únicamente este endpoint puede interpretar un `200 OK` como una creación completamente operativa, aunque el empleado todavía requiera una acción adicional para poder ser utilizado en Scheduler.

---

## Nota adicional — documentación

El body de ejemplo incluido en la colección Postman entregada con el reto utiliza `document_number`, mientras que el campo utilizado por el endpoint es `document_employee`.

Además, el ejemplo no incluye algunos campos que posteriormente aparecen en el flujo real del Dashboard, entre ellos `pay_rule_id`, `birth_date`, `timezone` y `pay_period_end`.
