# BUG-004: El backend de autenticación colapsa bajo carga concurrente mínima (503/504)

**Severidad:** Crítica
**Prioridad:** Crítica
**Componente:** API Gateway / servicio de autenticación — `POST /v1/login`
**Ambiente:** QA (https://demo.timekeeper.goodrabbit.tech)
**Reportado por:** Paula Gallardo Carrasco
**Fecha:** 25 de septiembre de 2026
**Encontrado mediante:** prueba de carga con k6 (bonus, `4-bonus/load-test.js`)

---

## Resumen

Bajo una carga de apenas **5 usuarios virtuales concurrentes**, el endpoint `POST /v1/login` falla en más de la mitad de los intentos con errores de infraestructura (`503 Service Unavailable` y `504 Gateway Timeout`), en vez de procesar la autenticación con normalidad. Los logins que sí tienen éxito bajo esta carga tardan entre 13.75 y 30.19 segundos (promedio 21.37s), peor que el peor caso ya documentado sin concurrencia (18.61s, ver `BUG-002.md`). Esto confirma y agrava el hallazgo de latencia de BUG-002: el problema no es solo que el login sea lento, es que el servicio detrás de él **no tolera concurrencia mínima**.

## Pasos para reproducir

1. Ejecutar el script de carga incluido en el repositorio:
   ```powershell
   $env:BASE_URL="https://demo.timekeeper.goodrabbit.tech"
   $env:QA_USER="admin"
   $env:QA_PASS="<contraseña>"
   k6 run 4-bonus/load-test.js
   ```
2. El escenario `login_load` sube gradualmente a 5 usuarios virtuales concurrentes durante 20s, los sostiene 40s, y baja a 0.
3. Observar la tasa de error y los códigos de estado de las respuestas fallidas (impresos en consola por el script).

## Resultado esperado

El servicio de autenticación debería sostener al menos unos pocos usuarios concurrentes sin devolver errores de infraestructura. Una tasa de error de 0% sería lo ideal; en el peor caso, degradación gradual de latencia, no fallos de conexión.

## Resultado actual

**Corrida con 5 VUs concurrentes (20s ramp-up, 40s sostenido, 10s ramp-down):**

| Métrica | Valor |
|---|---|
| Tasa de error en login | **54.54%** (6 de 11 intentos fallaron) |
| Latencia promedio (todos los intentos) | 21.37 s |
| Latencia mínima (incluso en éxito) | 13.75 s |
| Latencia máxima | 30.19 s (timeout del gateway) |
| p95 de latencia | 30.19 s |

**Errores capturados (código y mensaje real del Gateway):**

```
status=504 duration=30197ms body="upstream request timeout"
status=504 duration=30184ms body="stream timeout"
status=504 duration=30178ms body="stream timeout"
status=503 duration=15754ms body="upstream connect error or disconnect/reset before headers.
  reset reason: remote connection failure, transport failure reason: delayed connect error: 111"
status=503 duration=18581ms body="upstream connect error or disconnect/reset before headers.
  reset reason: remote connection failure, transport failure reason: delayed connect error: 111"
status=503 duration=16105ms body="upstream connect error or disconnect/reset before headers.
  reset reason: remote connection failure, transport failure reason: delayed connect error: 111"
```

## Análisis

- **`504` con mensajes `upstream request timeout` / `stream timeout`:** el API Gateway agota su tiempo de espera (~30s) sin recibir respuesta del servicio de autenticación interno.
- **`503` con `delayed connect error: 111`:** el código de error `111` corresponde a `ECONNREFUSED` a nivel de sistema operativo — el Gateway intenta abrir una conexión hacia el servicio de autenticación y esta es **rechazada activamente**, no solo demorada. Esto sugiere que el servicio de autenticación se queda sin conexiones disponibles (pool agotado) o no tiene réplicas/recursos suficientes para atender más de un puñado de solicitudes a la vez.
- El formato de los mensajes (`upstream connect error`, `reset reason`) es característico de un proxy tipo Envoy, consistente con la arquitectura de microservicios en clúster ya observada en `BUG-003.md` (`*.svc.cluster.local`).
- Esto explica, al menos parcialmente, el hallazgo de latencia de `BUG-002.md`: si el servicio de autenticación ya opera cerca de su límite de capacidad incluso con una sola solicitud a la vez (10-18s), es coherente que colapse por completo con una concurrencia mínima.

## Impacto

Este es el hallazgo de mayor severidad de todo el challenge. En un escenario de uso real, donde varios empleados o administradores inician sesión en un rango de tiempo corto (por ejemplo, al inicio de un turno), **más de la mitad de esos intentos de login fallarían**, bloqueando el acceso al sistema para la mayoría de los usuarios. Esto no es un problema cosmético ni de UX: es una falla de disponibilidad del servicio bajo condiciones de uso perfectamente normales, no bajo un ataque ni una carga extrema.

## Evidencia

Salida completa de la corrida de k6 adjunta (ver `evidencias/bug-004/` y `4-bonus/load-test.js`).

## Recomendación

Se sugiere al equipo de desarrollo:
1. Revisar la configuración de pool de conexiones y réplicas del servicio de autenticación en el ambiente QA.
2. Revisar los timeouts configurados en el API Gateway hacia el servicio de auth (actualmente ~30s, que ya es alto para una operación de login).
3. Repetir esta prueba en un ambiente de staging/producción con recursos equivalentes a los reales, ya que este hallazgo podría no reflejar el comportamiento de producción si el ambiente QA está deliberadamente subdimensionado.
